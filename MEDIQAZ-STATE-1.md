# MediQaz — состояние проекта

MediQaz — AI-ассистент для врачей в Казахстане. Врач записывает приём,
речь распознаётся, формируется медкарта (жалобы, анамнез, диагноз с МКБ-10,
назначения). Дальше медкарта должна попасть в МИС (Damumed/e-MIS), которую
использует поликлиника.

## Целевая архитектура передачи данных

Разделение ответственности намеренное: мобильное приложение и бэкенд не
общаются с МИС напрямую — это делает существующее расширение Chrome
(`mediqaz-extension`), которое уже умеет заполнять форму в Damumed/e-MIS через
инъекцию в страницу. Приложение и бэкенд для этой части — только источник
готовой медкарты.

```
Телефон (запись приёма)
        │  аудио уходит на бэкенд, на телефоне не хранится
        ▼
Бэкенд: Deepgram (транскрипт) → Groq (медкарта)
        │  генерация происходит на бэкенде, не на телефоне
        ▼
Телефон: врач видит готовую медкарту, нажимает «Отправить в МИС»
        ▼
Бэкенд пишет медкарту в Supabase (канал доставки, не хранилище) и шлёт
«дверной звонок» через Realtime — без пациента, без кода врача
        ▼
Расширение Chrome получает звонок и забирает медкарту через RPC,
проверяющую код врача (плюс догрузка при каждом открытии панели —
на случай, если браузер был закрыт в момент отправки)
        ▼
Врач в расширении подтверждает («Вставить в МИС» или «Позже»)
        ▼
Расширение заполняет форму в Damumed/e-MIS инъекцией
```

Звено «Отправить в МИС → Supabase → расширение» **реализовано в коде** (бэкенд,
мобильное приложение, `mediqaz-extension`), но по состоянию на эту запись:
**не закоммичено**, схема `docs/supabase/schema.sql` **не прогнана** на
Supabase-проекте, а сама доставка **не проверена end-to-end** на реальных
устройствах. Раздел «Что уже сделано» ниже помечает это отдельно.

Код расширения Chrome по-прежнему не переписывается целиком — точечные правки
под конкретные технические задачи (см. ниже) и формулировки для `ru.json`
(см. `TERMS.md`, откуда переносится глоссарий интерфейса).

## Активные поверхности

- **mobile** — основное приложение врача (Android в приоритете).
- **backend** — API, единственное место с ключами Deepgram/Groq и с
  секретным (service_role/secret) ключом Supabase.
- **webapp** — только панель одобрения администратором.
- **website** — отложено, не трогаем.
- **mediqaz-extension** (Chrome) — существующий инструмент ввода в МИС, вне
  этого репозитория по коду (`OneDrive/Рабочий стол/mediqaz1/mediqaz-extension`
  — актуальная копия среди нескольких на диске пользователя), но источник
  эталонных формулировок интерфейса. Теперь также получает медкарты через
  Supabase Realtime.

## Что уже сделано

### Первый путь врача (готово)
Регистрация → одобрение администратором (`isApproved`, вручную через веб-панель)
→ выбор специальности в профиле → бэкенд готов выдавать транскрипт-токен и
собирать медкарту → запись приёма на телефоне → просмотр готовой медкарты →
отправка в МИС. Весь путь реализован в коде от начала до конца (детали ниже);
не закоммичен и не проверен на реальном устройстве целиком за один прогон.

### Экран записи приёма (mobile)
Реальная запись через `expo-audio` (не заглушка) — мобильный экран «Приём»:
- Native background recording: конфиг-плагин `expo-audio` с
  `enableBackgroundRecording: true` в `app.config.js` — регистрирует Android
  foreground service и iOS `UIBackgroundModes`, запись не обрывается при
  блокировке экрана или уходе в другое приложение.
- Требует нативную пересборку — **не работает в Expo Go**. EAS dev build
  настроен (`eas.json` → профиль `development` с `developmentClient: true`,
  зависимость `expo-dev-client` установлена) и использовался для отладки на
  реальном устройстве в этой сессии.
- Обработаны нативные краевые случаи `AudioRecorder` из `expo-audio`: повторное
  нажатие «Начать приём» без остановки предыдущей сессии (`stopIfPrepared()`
  перед каждым `prepareToRecordAsync()`, включая путь сброса через
  `useFocusEffect`), корректный `Content-Type` при загрузке записи (сырые байты
  через `arrayBuffer()`, а не `Blob` с пустым `type` от `file://`-URI).
- Стек ошибок записи сбрасывается при возврате на вкладку (`useFocusEffect` +
  `useRef` для стабильности колбэка), а не остаётся зависшим из-за того, что
  Expo Router держит вкладки смонтированными.

### Экран медкарты (mobile)
После успешной отправки записи экран «Приём» показывает готовую медкарту, а не
только статус-плашку:
- 7 секций из `TERMS.md`/`MED_CARD_SECTIONS` (жалобы, анамнез, объективно,
  диагноз с МКБ-10, назначения, рекомендации, следующий приём) —
  `MedCardView`, компонует существующие `SectionCard`/`DataRow`.
- Формат медкарты сверен с тем, что ожидает `renderMedCard` в расширении
  (`MED_SECTIONS`, поля `текст`/`цитата`/`мкб10`) — совпадает полностью,
  маппинг не понадобился.
- Кнопка «Отправить в МИС» подключена к реальному эндпоинту (не заглушка,
  см. ниже), с повтором из любого терминального состояния.

### Доставка медкарты в МИС (Supabase Realtime)
Реализовано в коде, деталь архитектуры — см. диаграмму выше. Собственная схема
доставки, а не общий постоянный статус на общей таблице:

- **SQL** — `docs/supabase/schema.sql`. Таблица `medcard_deliveries` (канал, не
  хранилище: RLS включён, политик нет вовсе — доступ только у бэкенда через
  секретный ключ), таблица `delivery_signals` (безопасный «дверной звонок»:
  только `id`+`created_at`, ни кода врача, ни пациента, ни приёма), RPC-функции
  `claim_medcards`/`ack_medcard` (обе требуют код врача — это единственная
  граница безопасности, потому что публикуемый ключ расширения публичен по
  конструкции), Realtime-публикация только на `delivery_signals`, две
  cron-задачи очистки (просроченные доставки, звонки старше часа).
- **Почему не простой фильтр `postgres_changes`**: Realtime принимает только
  одно условие фильтра, и RLS всё равно применяется к самой таблице — фильтр
  по коду врача не даёт изоляции, только неудобство. Решение — «звонок» без
  данных плюс RPC с проверкой кода на чтение.
- **Backend** — `SUPABASE_URL`/`SUPABASE_SECRET_KEY`/`MIS_DELIVERY_TTL_HOURS` в
  `env.ts`; без них API продолжает работать, падает только доставка. Код врача
  (`users.mis_delivery_code`) выдаётся один раз при первом `GET
  /mis-delivery-code` (до первой записи приёма — врач сначала настраивает
  расширение) и может быть перегенерирован (`POST
  .../mis-delivery-code/regenerate`). Публикация — upsert в
  `medcard_deliveries` с явным `expires_at`, повторная отправка продлевает
  жизнь строки, а не наследует старый срок.
- **Mobile** — кнопка «Отправить в МИС» бьёт в `POST
  .../appointments/{id}/mis-delivery`, повтор безопасен (upsert на бэкенде), в
  профиле — секция с кодом врача (выделяемый текст, кнопки «Копировать» нет —
  `expo-clipboard` не в зависимостях) и кнопка сброса кода с подтверждением.
- **Extension** (`mediqaz-extension`, точечные правки) — подписка на
  `postgres_changes` по таблице `appointments`/`status=eq.ready` (общая для
  всех врачей, каждое расширение видело чужие карты) заменена на подписку без
  фильтра на `delivery_signals` + `fetchPendingMedCards()` через RPC
  `claim_medcards`. Догрузка при каждом открытии панели (`init()`), не только
  живые события — закрытый в момент отправки браузер больше не теряет карту
  безвозвратно. `ack_medcard` вызывается после того, как карта реально попала
  в `state.medCard` (и «Вставить», и «Позже»), автоскрытие баннера через 30
  секунд карту не подтверждает — она вернётся при следующем открытии.

**Не закоммичено.** Пользователь удалил первый тестовый Supabase-проект и
создал новый; `schema.sql` на новом проекте ещё не прогнана, ключи ещё не
проставлены ни в Railway, ни в настройках расширения. Сквозной прогон
(телефон → бэкенд → Supabase → расширение → МИС) ещё не выполнялся.

### Backend
Модули: `auth`, `users` (админ, одобрение), `consultations` (медицинское ядро:
Deepgram-грант, старт приёма, прогресс статуса, генерация медкарты через Groq,
вопросы по приёму, доставка в МИС), `notifications` (push), `storage`.

Специальность берётся из профиля врача на сервере, не из запроса клиента —
чтобы один врач не мог запросить промпт чужой специальности. Целевые эндпоинты
(`/med-card`, `/questions`) вместо универсального прокси к Groq — ключ и
промпт-правила не может обойти ни один клиент. Аудио удаляется сразу после
обработки, не хранится нигде.

### Локализация интерфейса
- Интерфейс полностью переведён на русский.
- Каркас i18n на русский и казахский (`ru.json`/`kk.json`, ASCII-ключи,
  кириллица только в значениях). Казахский пока — точная копия русского
  (`KAZAKH_TRANSLATION_READY = false`), переключатель языка скрыт в UI, пока
  не появятся настоящие казахские переводы — иначе это выглядело бы как
  рабочая функция, которой нет.
- Ошибки бэкенда переводятся по машинному коду, а не по тексту с сервера.
  Контракт (`packages/contracts/src/errors.ts`) отдаёт `{ code, message,
  params? }`; клиент ищет перевод по `code`, а `message` с сервера — только
  резервный текст и лог. Код у ошибки — специфичный по ситуации (например
  `APPOINTMENT_ALREADY_FINISHED`, `USERS_LAST_ADMIN`), не общий `CONFLICT`
  на всё подряд, кроме случаев, где ситуация действительно общая.
  **Старый бэкенд и новое приложение совместимы и в другую сторону**: если
  сервер уедет вперёд и пришлёт код, которого клиент ещё не знает, ответ всё
  равно парсится (код — открытая строка, а не закрытый enum на этом уровне),
  и врач увидит осмысленный текст сервера, а не пустоту или сырой код.
  Тест в мобильном приложении проверяет, что каждый код из
  `apiErrorCodeSchema` имеет перевод в `ru.json` — забытый перевод роняет
  тест, а не деградирует молча на экране врача.

### Починки
- Таб-бар — подписи вкладок обрезались снизу (высоты не хватало ровно на
  высоту подписи из-за `overflow: hidden` и того, как `insets.bottom`
  считался дважды). Исправлено.

## Долги и следующие задачи

1. **Прогнать `docs/supabase/schema.sql`** на новом Supabase-проекте — сначала
   включить `pg_cron` вручную в Database → Extensions (скрипт иначе упадёт на
   `cron.schedule`), потом прогнать целиком в SQL Editor.
2. **Проставить ключи после прогона схемы**: в Railway —
   `SUPABASE_URL`/`SUPABASE_SECRET_KEY`/`MIS_DELIVERY_TTL_HOURS`; в настройках
   расширения — Project URL (без `/rest/v1`), anon key, код врача из профиля
   мобильного приложения.
3. **Ротация ключей** — оба комплекта ключей (старого удалённого проекта и
   нового) были вставлены в чат открытым текстом. Старый проект удалён, но
   новый ключ стоит ротировать после первого прогона (Supabase → Settings →
   API → Rotate), чтобы секрет не жил в истории переписки бессрочно.
4. **Юнит-тест на `sendMedCardToMis`** (`consultations-service.test.ts`) — не
   написан; запрошен, но отложен пользователем в этой же сессии.
5. **Сквозной прогон на реальных устройствах** — телефон → бэкенд → Supabase →
   расширение → МИС, включая явную проверку случая «расширение было закрыто в
   момент отправки» (тот самый пункт 4 архитектурных требований).
6. **Коммит и пуш** — всё перечисленное в разделе «Доставка медкарты в МИС», а
   также экран записи и экран медкарты, лежит в рабочем дереве незакоммиченным.
   Естественная граница — два коммита: репозиторий (backend + mobile +
   contracts + `docs/supabase/`) отдельно от правок `mediqaz-extension` (вне
   монорепо, другой git — если он вообще есть).
7. **Настоящие казахские переводы** — после появления перевести `kk.json` и
   включить `KAZAKH_TRANSLATION_READY`.
8. **Railway env** — выставить `TRUST_PROXY=true`,
   `TRUSTED_PROXY_CLIENT_IP_HEADER=x-forwarded-for`,
   `TRUSTED_PROXY_CLIENT_IP_POSITION=last` (все три сразу — сейчас rate
   limiting может считать по IP прокси, а не клиента) и проверить это на
   реальном трафике Railway.
9. Локализация webapp (панели администратора) — намеренно не начата, отдельная
   задача при необходимости.
10. `docs/STORAGE.md` всё ещё описывает DigitalOcean Spaces — поверхность
    отложена, документ нуждается в пометке или обновлении под Railway/текущее
    хранилище.
11. README — остались секции про установку по шаблону, требуют чистки.
