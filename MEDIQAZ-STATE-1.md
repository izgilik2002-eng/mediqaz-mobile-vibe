# MediQaz — состояние проекта

MediQaz — AI-ассистент для врачей в Казахстане. Врач записывает приём,
речь распознаётся, формируется медкарта (жалобы, анамнез, диагноз с МКБ-10,
назначения). Дальше медкарта должна попасть в МИС (Damumed/e-MIS), которую
использует поликлиника.

## Целевая архитектура передачи данных

Разделение ответственности намеренное: мобильное приложение и бэкенд не
общаются с МИС напрямую — это делает существующее расширение Chrome
(`mediqaz-extension`), которое уже умеет заполнять форму в Damumed/e-MIS через
инъекцию в страницу. Приложение и бэкенд для этой части — только источник
готовой медкарты.

```
Телефон (запись приёма)
        │  аудио уходит на бэкенд, на телефоне не хранится
        ▼
Бэкенд: Deepgram (транскрипт) → Groq (медкарта)
        │  генерация происходит на бэкенде, не на телефоне
        ▼
Телефон: врач видит готовую медкарту, нажимает «Отправить в МИС»
        ▼
Бэкенд толкает медкарту в Supabase Realtime
        ▼
Расширение Chrome получает уведомление
        ▼
Врач открывает расширение, нажимает кнопку
        ▼
Расширение заполняет форму в Damumed/e-MIS инъекцией
```

**Важно:** на момент этой записи звено «Отправить в МИС → Supabase Realtime →
расширение» **не реализовано** — ни в бэкенде, ни на клиенте нет кода,
завязанного на Supabase. Это целевая схема для следующего этапа, а не
текущее поведение. Раздел «Что уже сделано» ниже описывает только то, что
подтверждено кодом.

Код расширения Chrome не меняется — трогаем только формулировки для `ru.json`
(см. `TERMS.md`, откуда переносится глоссарий интерфейса).

## Активные поверхности

- **mobile** — основное приложение врача (Android в приоритете).
- **backend** — API, единственное место с ключами Deepgram/Groq.
- **webapp** — только панель одобрения администратором.
- **website** — отложено, не трогаем.
- **mediqaz-extension** (Chrome) — существующий инструмент ввода в МИС, вне
  этого репозитория по коду, но источник эталонных формулировок интерфейса.

## Что уже сделано

### Первый путь врача (готово)
Регистрация → одобрение администратором (`isApproved`, вручную через веб-панель)
→ выбор специальности в профиле → бэкенд готов выдавать транскрипт-токен и
собирать медкарту. Экран самой записи приёма на телефоне (живой транскрипт,
wake-word) — ещё не построен, вкладка «Приём» пока заглушка.

### Backend
Модули: `auth`, `users` (админ, одобрение), `consultations` (медицинское ядро:
Deepgram-грант, старт приёма, прогресс статуса, генерация медкарты через Groq,
вопросы по приёму), `notifications` (push), `storage`.

Специальность берётся из профиля врача на сервере, не из запроса клиента —
чтобы один врач не мог запросить промпт чужой специальности. Целевые эндпоинты
(`/med-card`, `/questions`) вместо универсального прокси к Groq — ключ и
промпт-правила не может обойти ни один клиент. Аудио удаляется сразу после
обработки, не хранится нигде.

### Локализация интерфейса
- Интерфейс полностью переведён на русский.
- Каркас i18n на русский и казахский (`ru.json`/`kk.json`, ASCII-ключи,
  кириллица только в значениях). Казахский пока — точная копия русского
  (`KAZAKH_TRANSLATION_READY = false`), переключатель языка скрыт в UI, пока
  не появятся настоящие казахские переводы — иначе это выглядело бы как
  рабочая функция, которой нет.
- Ошибки бэкенда переводятся по машинному коду, а не по тексту с сервера.
  Контракт (`packages/contracts/src/errors.ts`) отдаёт `{ code, message,
  params? }`; клиент ищет перевод по `code`, а `message` с сервера — только
  резервный текст и лог. Код у ошибки — специфичный по ситуации (например
  `APPOINTMENT_ALREADY_FINISHED`, `USERS_LAST_ADMIN`), не общий `CONFLICT`
  на всё подряд, кроме случаев, где ситуация действительно общая.
  **Старый бэкенд и новое приложение совместимы и в другую сторону**: если
  сервер уедет вперёд и пришлёт код, которого клиент ещё не знает, ответ всё
  равно парсится (код — открытая строка, а не закрытый enum на этом уровне),
  и врач увидит осмысленный текст сервера, а не пустоту или сырой код.
  Тест в мобильном приложении проверяет, что каждый код из
  `apiErrorCodeSchema` имеет перевод в `ru.json` — забытый перевод роняет
  тест, а не деградирует молча на экране врача.

### Починки
- Таб-бар — подписи вкладок обрезались снизу (высоты не хватало ровно на
  высоту подписи из-за `overflow: hidden` и того, как `insets.bottom`
  считался дважды). Исправлено.

## Долги и следующие задачи

1. **Отправка медкарты в МИС** — реализовать целевую схему выше: кнопка
   «Отправить в МИС» на телефоне, пуш в Supabase Realtime на бэкенде, приём
   уведомления в расширении. Это отдельный и самый крупный оставшийся кусок
   архитектуры.
2. **Экран записи приёма** — живой транскрипт, wake-word, foreground-сервис.
   Не заработает в Expo Go, нужна сборка EAS dev.
3. **Экран медкарты** — просмотр результата на телефоне, кнопка отправки в
   МИС (зависит от пункта 1).
4. **Настоящие казахские переводы** — после появления перевести `kk.json` и
   включить `KAZAKH_TRANSLATION_READY`.
5. **Railway env** — выставить `TRUST_PROXY=true`,
   `TRUSTED_PROXY_CLIENT_IP_HEADER=x-forwarded-for`,
   `TRUSTED_PROXY_CLIENT_IP_POSITION=last` (все три сразу — сейчас rate
   limiting может считать по IP прокси, а не клиента) и проверить это на
   реальном трафике Railway.
6. Локализация webapp (панели администратора) — намеренно не начата, отдельная
   задача при необходимости.
7. `docs/STORAGE.md` всё ещё описывает DigitalOcean Spaces — поверхность
   отложена, документ нуждается в пометке или обновлении под Railway/текущее
   хранилище.
8. README — остались секции про установку по шаблону, требуют чистки.
